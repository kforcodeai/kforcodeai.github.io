  - level: 'design'
    q: 'Your harness compacts context on a locally computed token estimate. Why is that a cost bug, not just an accuracy detail?'
    a: 'A local estimator has a bias that varies with content — CJK text and reasoning-replay blobs can push a rough estimate to 2-3x real billed usage. Compacting on the estimate means firing at 35-55% of the real window: you pay a summarization call, stall the turn, and discard detail you did not need to discard. hermes-agent projects real usage from the last synchronized (rough, real) pair and compacts on the projection instead.'
  - level: 'design'
    q: 'Why would a harness gate context eviction behind a minimum reclaim of a few thousand tokens instead of evicting whenever it can?'
    a: 'Because eviction rewrites already-sent history, which invalidates the provider prompt-cache prefix from the earliest rewritten message forward. Without a minimum-reclaim gate a busy tool loop re-fires the prune almost every iteration, turning one episodic cache break into a per-turn one. The gate plus a trigger-sized rearm runway makes breaks episodic and amortized.'
  - level: 'staff'
    q: 'Automatic compaction fires every other turn and the context never gets smaller. What do you measure first?'
    a: 'The incompressible floor: system prompt plus tool schemas. Compaction can only shrink messages, so if the floor alone exceeds your trigger, every pass shrinks the transcript by a healthy margin and still leaves the prompt over the line. Measure floor size against threshold before touching the summarizer, then raise the trigger or cut the tool schema.'
  - level: 'staff'
    q: 'How would you add aggressive tool-result eviction to a harness whose defining constraint is prompt-cache stability?'
    a: 'Never rewrite mid-burst. Evict only at a boundary you are already paying for — a compaction commit, a session rotation, or a resume after the cache TTL has expired — so the break you cause is one you had already budgeted. Cap tool output at write time instead, since a result that was never large does not need evicting. Gate any commit on a minimum reclaim and require a trigger-sized regrowth runway before rearming.'
  - level: 'staff'
    q: 'A teammate proposes a slash command that reloads memory and rebuilds the system prompt mid-conversation. What is your review?'
    a: 'Reject the immediate form, accept a deferred one. Its own skill installer follows the rule; its MCP reload instead warns you it is about to break the cache.'
  - level: 'design'
    q: 'Where should the cache breakpoint go on a message built from a large static skill body plus a small volatile payload?'
    a: 'At the byte where the volatile tail begins, declared by the builder that concatenated them. In hermes-agent's config, the two cheapest ways to shrink a prompt both ship switched off, and the expensive one is the only thing left on. Everything interesting about the hermes-agent architecture follows from why.

The cheap ones are deterministic: dedupe repeated tool results, truncate oversized arguments, protect the recent tail, never call a model. The expensive one calls an LLM to summarize your transcript and hopes the summary was faithful. Every context ladder I would have written before this repo puts the deterministic passes first and summarization last.

NousResearch shipped it the other way round, and the comment beside each switch gives the same reason.

## One conversation that never ends

[hermes-agent](https://github.com/NousResearch/hermes-agent) is NousResearch's personal agent: one Python core behind a CLI, a terminal UI, a desktop app, editor integrations, cron, and a gateway that speaks about twenty chat platforms. Its compaction module alone is larger than most complete harnesses.

The size is not the interesting part. The workload assumption is. You talk to it from your terminal in the morning, your phone at lunch, a cron job overnight, and the design assumes this is one conversation, hundreds of tool results deep.

That assumption changes the arithmetic. A short session either gets the prefix discount or misses it, and the amount is small either way. Run the same conversation for a hundred turns and the prefix becomes the line item you pay again on every one of them, cached or uncached. The governing question stops being "how few tokens can I send" and becomes "how do I avoid re-pricing what I have already sent". That is a runtime problem more than a modeling one, which is the [layer I usually end up writing about](/blog/the-system-layer-behind-ai-products).

Six surfaces, one core, and a refusal to let any of them change what sits at the front of the prompt.

The frozen pair is the system prompt and the tool schema, both at the front of the cached prefix. Two breakpoints sit there and two roll forward with the last two cacheable messages, so each turn buys one cache write on the bytes it just added and every later turn reads them back at a tenth of the price. The provider reports a billed prompt-token count, and that number is what the two token-triggered reduction paths fire on.

## The constraint they wrote down

That refusal is not an implementation detail that happened to settle. Their development guide names two properties as the lens for reviewing any change, and this is the first:

<Callout label="from their development guide">

**Per-conversation prompt caching is sacred.** A long-lived conversation reuses a cached prefix every turn. Anything that mutates past context, swaps toolsets, or rebuilds the system prompt mid-conversation invalidates that cache and multiplies the user's cost. We do not do it (the one exception is context compression).

</Callout>

Their own pricing table supplies the numbers. One current model lists input at $5.00 per million tokens, cache reads at $0.50, cache writes at $6.25. I read this code rather than running it, so treat the rest as arithmetic on their figures. A cached read costs a tenth of a fresh read, and a cache write a quarter more than not caching at all. So a prefix you write and never read back is a loss, and one you read back once has paid for itself. Cache-breaking is a penalty charged up front, plus full price to re-ingest everything behind the break.

The rule reaches into the product, and where it stops is instructive. Any slash command that mutates system-prompt state is supposed to defer the invalidation to your next session, unless you ask for it now and accept the bill. Installing a skill does. Reloading MCP servers takes effect immediately, behind a modal titled as a prompt-cache invalidation warning.

One limit on all of this gets skipped in most writing about prompt caching: a cached prefix has a lifetime, and the shipped default here is the five-minute tier, with an hour available on request. So the morning-terminal-to-lunch-phone story reuses nothing. The prefix is long cold and the first turn back pays a fresh write. The contract binds hard inside a burst of turns and not at all across the gaps between them, which is where the interesting opportunity turns out to live.

## The prune that ships switched off

If a rewrite is a penalty, then within a burst the cheap reclaimers are not cheap.

The deterministic prune is the pass I would put first in any other harness. It walks old tool results, drops duplicates, summarizes oversized ones without a model, truncates bulky call arguments, and leaves the full output recoverable. Its trigger ships at zero, and the comment beside it gives the reason in one sentence: each committed prune rewrites already-sent history, breaking the provider prompt-cache prefix.

Micro-compaction folds the oldest unabsorbed exchange into a rolling summary after each turn, and it is off for the same reason at more length: a pass rewrites already-sent history, so it breaks the prefix every turn. Enable it, the comment says, only once you have measured that the amortized stall beats the discount. A cadence knob will run a pass every Nth turn instead, which looks like the rescue the prune gets from its minimum-reclaim gate. It isn't: a counter fires on turns elapsed, the gate on tokens reclaimed, and only one of those can promise a cache break bought something.

So the shipped ladder is: nothing, then nothing, then one large summarization at three-quarters of the usable input budget on any model under 512K, which is most models in use today. Backwards by the usual advice, and defensible inside a burst. Eviction is free only when the deleted tokens are the only thing you pay for, and in a cached conversation, deleting one from the middle re-prices every token behind it.

I went in expecting to file those zeros as an oversight, a half-built feature left switched off. It isn't that. The zero is the decision, and the feature is there for the workloads where the arithmetic tips.

| The ladder | What it saves | What it costs |
|---|---|---|
| Prune on by default, the usual advice | The dead tool-result tokens on every later turn in the burst | A prefix re-ingest from the rewrite point forward, each time it commits |
| Prune off, carry the junk instead | Nothing. The junk rides along in history | Cached re-sends at a tenth of fresh input, and window: dead tokens pull the lossy summarization forward |
| Micro-compaction on, every turn | On their published run, occupancy flattened at about a fifth of the threshold and batch compaction never fired at all | A broken prefix every turn, and a stall per pass of two to thirty-seven seconds, median around thirty-one, on one contended local model |

Those columns are honest about money and vague about accuracy. Carrying junk is priced as cheap tokens, but stale tool output is not inert, and a superseded file listing is something the model can read and act on. Nothing in the repo measures that and neither can I from reading it, so treat row two's accuracy cost as unknown rather than zero. Neither pass is destructive on disk, since both archive the original rows and leave them searchable, so the accuracy question is only about what the model can still see.

## Four thousand tokens, or it doesn't commit

Someone does switch the prune on, and the comment names the workload. It is a large-window model where the threshold rarely fires, so bulky terminal dumps and file reads ride along in history and get re-sent on every turn.

A prune only commits if it reclaims about four thousand tokens, which is about the token weight of two oversized tool results by the repo's own definition of oversized. The reason is obvious in hindsight: a prune that fires whenever it *can* fires on nearly every iteration, because each new tool pair ages an older one out of the protected tail. Every one of those fires is a cache break, so the gate demands a meaningful batch before paying for one.

The part I would not have thought of is what happens next. After a commit, the next prune is blocked until the prompt regrows a runway at least as large as what was just reclaimed, and the watermark is written to disk alongside the compacted rows. Someone worked out that a restart is the obvious way to defeat a cooldown held in memory, and closed it.

```
# a prune only commits if it clears the gate
reclaimed = before - after
if reclaimed < MIN_RECLAIM:          # a few thousand tokens
    keep the junk, try again later

# then it must wait out a runway before re-arming
runway   = max(reclaimed, trigger, MIN_RECLAIM)
rearm_at = after + runway            # persisted with the rows
```

Hysteresis is not free: junk lives in context for up to a full runway longer than it needs to, and a batched schedule drops a different set of messages than an eager one would. Against a per-turn cache break it is still cheaper.

Now put that gate together with the five-minute TTL, because the combination points somewhere the defaults do not go. A prune is expensive when the prefix is warm and free when it is cold, and the coldest moment in this workload is the one the product is built around: you come back after lunch. Hermes has machinery for exactly that moment. Idle compaction — opt-in, shipping at zero like the others — fires when a session resumes after a configurable gap, above a size floor, and pays for a full summarization before the first reply. Which is the expensive reclaimer arriving at the cheap boundary, with the cheap one wired to nothing. That is a third zero, and the one I would argue hardest about. The code justifies it as not re-reading stale context and never says the quiet part, which is that a resume is the one boundary where a rewrite costs nothing, because there is nothing left to invalidate. Prune hard on resume, never mid-burst, is the rule this architecture implies and stops short of adopting.

## What if the number that fires it is wrong?

Every gate above is downstream of one quantity: an estimate of how large the next request will be. That estimate is wrong in every harness I have read, and this repo is unusual in treating the error as measurable rather than as a rounding allowance.

Their estimator deliberately over-counts so that compaction happens before a provider rejects the payload, but the margin is not a fixed percentage. Their own note puts CJK text at about seventy percent over its real cost, and reasoning-replay blobs at several times theirs. A heavy session can therefore show a rough estimate two to three times real usage, and compact at a third to a half of the real window. Compacting a window you believe is nearly full and isn't means a summarizer call you did not need, a turn nobody needed stalled, and detail discarded for nothing.

So they close the loop. The rough estimate is recorded before each call, paired with the provider's billed count when the response arrives, and re-anchored on every response whose prompt fit rather than only after a compaction. The trigger fires on the projection.

```
before the call:  rough = estimate(messages, tools)
after the call:   real  = response.usage.prompt_tokens
                  if the prompt fit: baseline = (rough, real)

# fire on the projection, not the raw estimate
growth    = max(0, rough_now - baseline.rough)
projected = baseline.real + growth
if projected >= threshold: compact()
```

The blind spot follows from the shape of it. The projection corrects bias it has already observed, then trusts the new increment at face value, so what it cannot see coming is a fresh paste of exactly the content the correction exists for. The module is candid: the projection is not a strict upper bound for Cyrillic, Greek, Thai or Arabic, and it names two backstops, a real reading at or above the threshold clearing the baseline and a provider overflow error still triggering compaction. How much it buys on a typical session I cannot tell, since nothing reports corrected against raw triggers.

## Asking, afterwards, whether it worked

That calibrated trigger tells you when to compact and says nothing about whether compacting helped. The second half of the loop is where this harness stops resembling the others.

Effectiveness here means one thing: did the prompt get under the threshold, judged on the provider's billed count for the conversation just compacted. A shrinking message list does not count, and the reason is a floor compaction cannot touch. Compaction only shrinks messages, while the system prompt and tool schemas are incompressible. So when the floor alone meets the threshold, "every pass shrinks messages by a healthy margin yet leaves the prompt over the line, so the next turn compacts again, forever."

A post-compaction reading still over the line records a strike. Two strikes trip a breaker, and after five minutes of block one probation probe is allowed, with the counter dropped to a single strike so a bad probe re-trips at once. Counters are durable per session, and the recovery clock arms on the first blocked evaluation rather than at trip time, so a process restarting into a tripped guard starts a full window blocked. Tripping buys an end to paying for passes that reclaim nothing. It leaves a session that can only grow toward the provider's hard limit. Read the breaker as a diagnosis rather than a repair: your floor is too big, and no schedule of summaries fixes a floor.

It took me a while to read the pass correctly. I spent a good hour convinced compaction ran beside the turn, because the call site hands the whole thing to a pooled daemon thread behind a commit fence. It does not. The turn still waits; what the thread buys is that work missing its deadline is discarded rather than half-applied. Their published run puts a micro-compaction pass at two to thirty-seven seconds, median around thirty-one, and a batch pass summarizes far more transcript than that while someone waits on a turn they asked for.

## The floor is one they chose

That floor is the one number nobody can compact their way out of, so it pays to be exact about it.

Their reasoning for it is good and written down. The core as a narrow waist with capability at the edges is the second of those two review lenses. The stated reason is the right one — every model tool they add is sent on every API call, so the bar for a new core tool is high. A footprint ladder pushes new capability toward a CLI command plus a skill, then service-gated tools, then plugins and MCP servers, with a core tool as the last resort. Most projects have nothing like it, and the always-available surface is the product: one agent that does the thing wherever you are talking to it, which you cannot ship with eight tools.

The core list runs to fifty-nine tools, shared by the CLI and every messaging-platform toolset. How many reach a given request depends on a per-tool availability check: smart-home control needs a token, the kanban set needs a worker or a profile that enables it, computer use needs a driver. So the number is configuration-dependent and lower, while their own comment still budgets the floor at twenty to thirty thousand tokens with fifty-plus tools. Six of the entries are the video block: four generators, a result poller, a prompting guide, all visible to anyone signed in. A cron job that files a nightly report pays to describe video generation on every call.

The part that took me longest to see is that the floor is cheap in money and expensive in window. No prune touches it, and the stable tier of the prompt survives a compaction, so ordinary turns re-read it at a tenth of the price. The compaction turn is the exception: it replaces the history and rebuilds the prompt, which a comment in the loop calls a cold write on any endpoint. You therefore re-pay the floor once per compaction rather than once per turn, which is one more reason to compact later than sooner. It is also why the trigger has to be raised to three-quarters on sub-512K models, and their comment says what happens otherwise — the floor eats most of the reclaimed headroom, compaction re-fires every turn or two, and the session spends its wall clock summarizing. So the schema does not really cost these users money. It costs them the ability to stop summarizing, which is why the surrounding machinery has to exist.

I have made a version of this argument before, about [23 models that were an architecture problem wearing a modeling costume](/blog/one-model-instead-of-23). The honest version here is narrower: the count is the price of the product promise, and none of the cache discipline reduces it.

## What travels, and what doesn't

Take the cache contract away and most of this machinery loses its justification, which makes the defaults the wrong thing to copy.

If your provider has no prefix cache worth protecting, or your agent is stateless per task, adopting these zeros hands you no eviction, no amortization, and one lossy summarization at the threshold. They are correct because of a constraint you may not share.

The calibration loop travels, and it is the one thing here I would put into my own system tomorrow. Record the rough estimate before the call, pair it with the provider's reported prompt-token count when the response lands, and trigger reduction on the projection instead of the guess. Then take the second half, since it is the same signal doing more work: after compacting, check the next real reading against the threshold, and if you are still over, stop, because your floor is the problem. It needs a reported token count, which most provider APIs return; a local endpoint that reports nothing, or a model switch mid-session, puts you back on the raw estimate.

Ordering is the thing that will bite you, and it never announces itself. Cache decoration has to run dead last, after every other mutation of the transcript. Marking a message rewrites its content from a plain string into a block list, so a later normalization pass that type-checks for a string skips it. A tool result ending in a newline then ships unstripped while it sits in the marked window and stripped once it rolls out: same message, different bytes on consecutive turns, breaking the prefix where the breakpoints existed to protect it. Weeks later it surfaces as a sag in cache-hit rate with no error anywhere. Hermes gets the order right and explains it in a comment. If you build a cache plan, make it an assertion.

Most harnesses never state their denominator. This one optimizes for the turn economics of a long-lived conversation, specifically the cached prefix. It does not optimize input-token count, which it will let grow rather than rewrite history. Nor cost per successful task — though the calibration loop and the breaker come closer than most, since both exist to stop the harness spending money on work that produces nothing. The gap is precise: these mechanisms catch wasted harness work, not wasted task work. Nothing here notices that the agent got the answer wrong and is about to try again, and that retry is what actually decides your bill.

## Where this leaves us

The rule I am keeping is narrower than the one I arrived with. Cheap context reduction never touches bytes the provider has already seen, and the next cheapest happens at a boundary you were already paying for. A compaction commit is one. So is a cache expiry, which is the boundary this repo built a mechanism for and left switched off.

What stays open is where the rewriting happens at all. The durable record here is already append-only in the sense that matters: a compaction archives the pre-compaction turns rather than deleting them, and they stay on disk and searchable under the same session. What gets rewritten is the outgoing request, and that is what the gates and counters protect. So the question for the next harness is why the request is assembled by editing history rather than projected from it, so what the model sees can change without changing what the provider has seen.
